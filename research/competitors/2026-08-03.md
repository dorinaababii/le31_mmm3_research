### Open-source POS / restaurant management

- **TastyIgniter** — [homepage](https://tastyigniter.com/), [GitHub](https://github.com/tastyigniter/TastyIgniter) (3,683★)
  - Stack: PHP / Laravel + MySQL; MIT-licensed (3.x). Owns the "online ordering + table reservation" niche.
  - Pricing: open-source (self-host); commercial "extensions marketplace" on tastyigniter.com.
  - Features (from tastyigniter.com/features/): online ordering, table reservation, kitchen display, multi-location, multi-language, customer review system, customisable order types, discount/promotions, Stripe + PayPal + Mollie + Authorize.net + Square payments, extension marketplace, unlimited menus.
  - Standout: extension marketplace — third-party add-ons cover inventory, loyalty, payroll, etc., without bloating core.
  - Gap vs. LE31: stock for **prepared** items is a generic inventory module (treats prepared food like any SKU), not a per-batch qty-remaining ledger; no first-class cook bot; no concept of "today's prep quantity consumed" auto-hiding sold-out items.

- **Floreant POS** — [homepage](http://floreant.org/), [GitHub mirror (Jabro fork)](https://github.com/Jabro/floreantpos)
  - Stack: Java Swing (desktop POS); MySQL/PostgreSQL.
  - Pricing: open-source (GPL).
  - Features (from Jabro README): order management, kitchen automation, cash control, takeout tax split, coupon/gift cards; runs on Windows/Linux/macOS/Java tablets.
  - Standout: long-running Java desktop POS; wide hardware support (touch screens, printers, cash drawers).
  - Gap vs. LE31: desktop-only (no web UI for waiters), no Telegram integration, no prepared-batch stock, Java stack is heavy for a single small restaurant.

- **uniCenta oPOS** — [homepage](https://unicenta.com/), [GitHub mirror (DeanBeer)](https://github.com/DeanBeer/uniCenta-oPOS)
  - Stack: Java (forked from Openbravo POS).
  - Pricing: open-source (GPL) + paid "uniCenta Cloud" hosting.
  - Features: POS, touch-screen UI, table management, stock control, reports, multi-store, gift cards/loyalty, hardware integration.
  - Standout: very large feature list including loyalty; commercial cloud option.
  - Gap vs. LE31: prepared-item per-batch stock is generic stock-control, not a first-class finite-prep ledger; Java desktop, not web+Telegram; no first-class cook bot.

- **SambaPOS** — [homepage](https://sambapos.com/), [GitHub mirror (emreeren)](https://github.com/emreeren/SambaPOS-3)
  - Stack: C# / .NET (Windows).
  - Pricing: freemium (free base + paid modules; pricing gated, not reachable from curl).
  - Features: touch-screen POS, table management, kitchen tickets, inventory, loyalty, multi-store, payment integrations, scripts engine.
  - Standout: scriptable actions engine — operators can customise flows without code changes.
  - Gap vs. LE31: Windows-only desktop, no Telegram, no prepared-batch first-class concept, paid modules behind pricing wall.

- **ERPNext Restaurant module** — [homepage](https://frappe.io/erpnext), [GitHub](https://github.com/frappe/erpnext) (GPL-3.0)

  - Standout: breadth — every back-office function (tax, payroll, accounting) is integrated, not bolted on.
  - Gap vs. LE31: 100x heavier than LE31; restaurant "POS" is generic; per-batch prepared-item ledger is achievable only via custom Frappe Doctypes or the Batch module (which tracks lot IDs, not "today's prep quantity" decrementing in real time).

- **URY** (URY-ERP) — [homepage](https://github.com/ury-erp/ury), [GitHub](https://github.com/ury-erp/ury) (326★) + [URY Mosaic KDS](https://github.com/ury-erp/mosaic) (45★)
  - Stack: TypeScript/Python on top of ERPNext/Frappe.
  - Pricing: open-source (GPL); Frappe Cloud marketplace lists "URY" as deployable.
  - Features: POS (dine-in, takeaway, delivery, offline mode, printer management), KDS (URY Mosaic, real-time order queues, KOT printing), P&L dashboard, consumption reports, item-trend reports, production units, multi-kitchen routing.
  - Standout: **integrated to ERPNext** — KDS feeds into accounting + inventory without glue code; "in active use at 10+ outlets for 10+ months" (self-reported on README).
  - Gap vs. LE31: no Telegram surface; prepared-item stock via ERPNext Batch (heavyweight, lot-based, not a real-time per-prep decrement); still ERPNext deployment cost.

  - Standout: **POS-agnostic** — designed to be the KDS component in a multi-app stack (matches LE31's potential `sse-cook-channel` pick from the 2026-08-03 daily research).
  - Gap vs. LE31: no kitchen-ticket creation logic, no order flow, no Telegram; needs to be paired with a separate POS. Not a system, a component.

  - Pricing: open-source (no license file confirmed; stack: typical MIT).

## LE31_GAP_ANALYSIS:

Features competitors integrate that LE31 does **not** ship. Ranked by **likelihood of relevance to a single small restaurant** (the LE31 charter §3.1 explicitly says "one restaurant, one location, no multi-tenancy"), so a feature that's only useful at scale (multi-location, payroll, capital) is ranked low even when present in every SaaS.

### Tier A — High relevance, no real cost to add (would be the next 3 v1/v2 picks)

1. **A standalone KDS surface (or SSE cook channel)**
   - Source signal: TastyIgniter (dedicated KDS extension), URY Mosaic (whole app), KamerrEzz `restopro_kds`, OpenKDS, CampusBites, FoodStreams — **every multi-outlet kitchen system has one as a separate surface**, not a tab in the POS.
   - LE31 has the Telegram bot, which is the *input* side of the cook surface, but **no live "tickets waiting" / "running low" screen**. The 2026-08-03 daily research already queued `sse-cook-channel` as Pick A; this competitor survey independently confirms the gap.
   - Why high: even a single small restaurant, one cook, benefits from a glanceable live screen (phone in pocket, eyes on the pan).

2. **Per-item modifier support** (size, extras, "no onions")
   - Source signal: TastyIgniter (dish & modifier management), KamerrEzz `restopro_tables` README, `ahmedali5530/restaurant-pos` ("dish & modifiers management"), TouchBistro (iPad-first), Toast.
   - LE31 charter §3.2 explicitly defers modifiers; but the moment you sell a single pizza place, modifiers ("half-and-half", "no cheese") become non-optional.
   - Why high: one-table-of-restaurant owners hit this within a week of going live.

3. **Per-shift tip pooling / distribution**
   - Source signal: Toast, Square, Lightspeed — every full SaaS has it.
   - LE31 charter §3.2 defers tip pooling; only "tip derived from total_paid − items − tax" is in v1.
   - Why high: in a French brasserie, "pourboires partagés" is a 1-day-a-month conversation. Even a small "shift tip ledger" is enough to defer it.

### Tier B — Medium relevance, real cost to add

4. **Payment gateway integration (Stripe / SumUp / Zettle)**
   - Source signal: every SaaS has it; SumUp + Zettle are EU-relevant for a Paris restaurant.
   - LE31 charter §3.2: "We record `method = cash | card` only" — deferring is correct for v1, but a v2 must at least record the **card-payment** operator with a manual reference (SumUp/Zettle have email receipts that LE31 could ingest as evidence).
   - Why medium: adds ops complexity (PCI scope, key management) and a real-world integration (SumUp API in France is a paid partnership). Worth deferring until the owner asks.

5. **Reservations**
   - Source signal: TastyIgniter (table booking system, first-class feature), RestoBot, TouchBistro, Lightspeed, Toast.
   - LE31 charter §3.2: out of scope for v1.
   - Why medium: Paris restaurants use TheFork or Google Maps reservations; building your own is a poor second choice. The right answer is "integrate with TheFork API", which is a future v2.

6. **Loyalty / repeat-customer tracking**
   - Source signal: Toast, Square, Lightspeed, TouchBistro, Clover, RestoBot.
   - LE31 charter §3.2: out of scope.
   - Why medium: a 40-seat restaurant with a regular clientele gets a loyalty ask within 6 months, but the operator cost (CRM data, GDPR) is non-trivial.

7. **Cash-shift variance report with bank-deposit reconciliation**
   - Source signal: Floreant ("cash control"), Toast, Square, Lightspeed — all have end-of-shift expected-vs-counted.
   - LE31 charter §2 P1 calls this out as an acceptance criterion (`Shift.variance` exists). **This is on the LE31 roadmap and being built**; competitor confirmation only.

8. **CSV / PDF daily-report export**
   - Source signal: TastyIgniter, Toast, ERPNext, Odoo — all of them.
   - LE31 charter §2 P2: `GET /api/reports/today.csv` returns text/csv. **Already on the LE31 roadmap (P2).**

### Tier C — Low relevance for a single small restaurant (out-of-charter, would be re-evaluations)

9. **Multi-location support** — every SaaS, every FOSS ERP. LE31 charter §3.1 is explicit: no. The `Visit.server_id` field already exists for a future revisit; defer.
10. **Online ordering / customer-facing QR code menus** — `satisfecho/pos` (per-tenant QR + Stripe + Revolut), `BryanTheLai/RestaurantProject`, CampusBites, TouchBistro. Charter §3.2: out of scope. A QR menu is a 1-day v2 pick if a single restaurant wants it; the operator's existing TheFork/web page covers it.
11. **Payroll / staff scheduling** — Toast, Square, Lightspeed, ERPNext, Odoo. Out of charter; owner is a single shop.
12. **Marketing / email-campaign engine** — Square Marketing, Toast Marketing, Lightspeed Marketing. Out of charter.
13. **Toast Capital / Square Capital / Lightspeed Capital** — SMB lending products. Out of charter; owner is non-technical and the feature is an anti-pattern for a small operator.
14. **In-app analytics / forecasting** — `awgdawg/restaurant-forecast-analytics` (Toast → Databricks + Prophet), `ahmedali5530/restaurant-pos` (AI Reports), Toast BI, Lightspeed Analytics. **LE31 charter §2 P1 calls for `/api/reports/today` + `/forecast` (avg_14d × 1.1)**; the 7-day prep forecast is in scope, a full analytics layer is not.
15. **AI menu recommendations / customer-facing AI** — RestoBot (YandexGPT), `ahmedali5530/restaurant-pos` (AI Reports). Charter §3.2: no customer-facing AI; the cook-facing `/forecast` is the LE31 equivalent.

## KILLER_FINDINGS:

1. **No FOSS or SaaS competitor implements per-batch prepared-item stock as a first-class concept.** OpenAlex returned 0 papers on the topic; the GitHub topic searches returned 0 repos; the TastyIgniter extensions marketplace has no "prepared batch" extension; the Odoo/KamerrEzz module does it via Odoo's generic stock; ERPNext's Batch module is lot-tracking, not "today's prep quantity decrementing in real time". **LE31's append-only `StockEntry` ledger remains a defensible killer differentiator**, and the daily research note from 2026-08-03 is independently re-confirmed.

2. **Telegram-first restaurant ops is an empty niche.** `aiogram+restaurant+language:python` returned 0 repos pushed in the past week, and the broader topic search returned only RestoBot (Russian SaaS, 3★), `mary3000/telegram-restaurant-bot` (12★, generic), and a handful of Wolt-scraper bots. **No FOSS or European-market Telegram-driven restaurant POS exists.** LE31's `cook Telegram bot + waiter web UI` split is not just unusual — it's unoccupied, both in the LE31-relevant market (small EU restaurants) and the open-source community at large.

3. **Every KDS-class competitor is a separate surface, not a Telegram bot.** TastyIgniter's KDS extension, URY Mosaic, KamerrEzz `restopro_kds`, OpenKDS, CampusBites, FoodStreams — **all are real-time web UIs with screen-glanceable cards**, not chat surfaces. The LE31 Telegram bot is the cook's *input* surface; the missing peer is the **live "tickets waiting / running low" screen**, which is what every competitor proves is essential. This validates the 2026-08-03 daily research Pick A (`sse-cook-channel`).
